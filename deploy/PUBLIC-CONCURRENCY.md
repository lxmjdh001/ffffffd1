# 公共入口并发验证

目标：APK、PWA、斗篷和应用分流入口**合计持续 200 请求/秒**，包括流量集中于同一客户的情况。这里的入口吞吐量不等于 APK 文件传输带宽，也不等于 200 个安装完成事件/秒。

## 本次实现

- 分流读取不再锁客户余额行。随机分流共享锁定当前分流，顺序分流独占锁定当前分流的游标；配置编辑、删除先锁分流再替换链接，避免并发请求读到新旧配置的混合状态。余额扣费仍保留事务锁。
- 访问统计使用容量 4,096 的队列，每 100 毫秒或满 128 条批量写入。正常请求不等统计 INSERT 完成。只有统计进入该队列，扣费、下载凭证和广告回传仍使用各自的原有事务与任务机制。
- 队列溢出或数据库写入失败时，将统计写入 `DATA_DIR/visit-journal`，随后恢复。重放按记录 ID 幂等；损坏文件移入 `visit-journal/invalid` 保留检查。正常关闭服务会排空队列。
- APK 可用性和账号状态合并查询；限流计数通过原子的 `INSERT ... ON CONFLICT ... RETURNING` 一次取得。缓存编译产物的静态 manifest，避免每次渲染重复解析。
- 访问记录保持 35 天保留期；过期清理从每小时最多 5,000 条改为每分钟最多 20 批、每批 5,000 条，单轮最多执行 2 秒。多副本共用分钟限流，分批提交避免长事务。实际清理速度受数据库性能限制，仍需监测积压。

不缓存访客 HTML、域名归属、斗篷规则、广告凭证或余额。因此复制域名、语言匹配、规则更新和租户隔离继续实时判断。风险检测仍在后台执行，分流仅读取已保存的结果和兜底规则。

## 配置更新与缓存核对

本次没有实现原先讨论的业务配置短时缓存。唯一新增的服务端缓存是二进制内嵌静态资源 manifest；它属于构建产物，只随新版本进程更新，不包含客户配置。以下配置保存成功后，后续公共请求直接读取数据库，不需要等待 TTL：

| 修改入口 | 公共请求读取 | 控制台刷新 |
| --- | --- | --- |
| 斗篷规则、目标、三种状态、删除 | 每次读取斗篷及客户状态 | 保存成功后失效当前控制台查询缓存 |
| 分流链接、标识、顺序/随机、启停、删除 | 事务内读取分流及链接；风险结果由后台更新后读取 | 同步失效应用下载按钮的分流候选及斗篷候选 |
| APK 直下/详情页、应用资料、启停、标识、安装包、删除 | 每次读取应用和可用性 | 原有全局失效继续保留 |
| APK 详情页、多语言、回流、分流按钮关联 | 每次读取已发布的页面设计及关联 | 页面保存后同步失效应用与候选列表 |
| PWA 配置、图标、启停、删除 | 每次读取 PWA 与落地页配置 | 同步失效斗篷、广告、导入候选及工作台 |
| 广告关联、快速/深度配置、渠道开关、Token、API 密钥、删除 | 接口及投递任务读取当前广告配置 | 失效配置、关联应用和凭证查询；删除时移除凭证缓存 |
| 客户域名、管理员公共域名及使用范围 | 每次读取域名归属和平台设置 | 域名变更原有失效保留；平台设置保存后补充全局失效 |

前端的全局失效在写接口成功后执行：已挂载的查询重新请求，未挂载的查询标记过期，在重新进入时读取。这样不依赖手工维护容易遗漏的跨页面 query key 列表。它仅发生在管理操作后，不增加公共访问的数据库查询次数。保存失败不会按保存成功处理；PWA 已保存但图标上传失败时，仍刷新已经成功保存的配置。

动态公共响应采用 `Cache-Control: no-store`；PWA manifest/Service Worker 使用需要重新验证的缓存策略。归因、下载凭证、余额及扣费状态没有纳入共享页面缓存。已打开的落地页不会被远程强制改写，需要刷新或发起新请求；其他浏览器窗口也不通过这次本地查询失效即时推送更新。已经创建的事件、票据和执行中的请求遵守各自的校验及事务规则，不把历史快照误当作页面配置缓存。广告 Pixel 变更时，旧投递不会悄悄改投新 Pixel。

核对覆盖斗篷、分流、APK/PWA 配置、多语言详情页、域名使用范围、广告配置与凭证相关后端回归，并补充前端跨页面失效检查。若以后加入业务缓存，需要重新实现并验证所有写入口（包括 API、管理员操作及后台任务）的失效，不能把本次核对作为尚未实现缓存的有效性证明。

## 统计持久性边界

访问统计通常延迟约一个刷新周期显示。数据库故障或队列溢出时，异常路径会进行本地文件写入；磁盘阻塞仍可能延迟这个路径。突然断电或 `SIGKILL` 可能丢失尚在内存中的统计尾部；正常停机成功排空时不丢失队列记录，超过停机期限则记录错误。金融账本和广告任务不经过此队列，不受此统计尾部窗口影响。

部署时应保留并监测 `DATA_DIR` 可写空间，关注 `visit statistics deferred to journal`、`visit statistics journal failed` 和 `visit writer shutdown incomplete` 日志。日志积压表明数据库或磁盘需要处理，不能靠无限增加队列掩盖。

## 可重复的隔离测试

使用专用 PostgreSQL 测试库，不允许填写生产连接。测试自动创建和删除独立 schema；使用虚构账号、100 字节的本地文件和虚构广告配置。不会调用支付或广告平台，不会修改客户数据。

```sh
TEST_DATABASE_URL='postgres://testuser@localhost/d1_load?sslmode=disable' \
D1_LOAD_TEST=1 D1_LOAD_QPS=200 D1_LOAD_SECONDS=60 D1_LOAD_CASE=mixed \
go test ./internal/platform -run '^TestPublicEntryLoad$' -count=1 -v -timeout=10m
```

`D1_LOAD_CASE` 可选 `mixed`、`apk`、`pwa`、`cloak`、`traffic`。定时产生请求，不等上一请求完成后才发下一请求；延迟包含压测端调度积压。并发上限 256，排队溢出或请求错误均算失败。每次请求使用独立 IP 和新的访客上下文，所有请求集中在同一个账号、同一组资源；顺序分流使用同一个游标。

开启 `D1_LOAD_WITH_BILLING=1` 后，在入口流量之外，部分访客执行下载、重复下载，以及安装开始、确认或取消。APK 重复请求首字节三次，PWA 重复提交最终状态两次。独立运行 `RunDownloadAdWorker` 准备本地广告任务，等待其处理完毕，再校验赠送余额优先抵扣、现金余额、冻结金额、收费事件数量、取消安装不扣费和广告任务去重。不会运行向广告平台发送 HTTP 请求的 `RunAdWorker`。它模拟客户端调用安装确认接口，不替代真实设备的安装事件测试，也不验证广告平台是否接受回传。

每次测试输出一行 `LOAD_REPORT` JSON。SQL 次数包含请求及统计批次；计费场景还包含额外业务请求，不能直接和纯页面 SQL 次数比较。响应状态 302 仅用于独立分流入口；斗篷落地页必须为 200 且不能有 Location，分流目标必须保留配置的客户域名。所有统计记录数量必须匹配，纯页面流量不得产生扣费或广告转化。

候选版本另外完成了 **60 秒、12,000 次入口请求 + 7,000 次业务 API 请求**：页面 P95 36.69 ms、P99 61.06 ms，无失败或连接池等待，18,000 条访问统计完整。此处页面延迟不代表整段安装或文件传输耗时。

- 1,000 个 APK 访客，每个重复请求首字节 3 次，产生 1,000 次收费；独立队列生成 1,000 个转化和 1,000 个广告投递任务。
- 500 次 PWA 安装确认、500 次取消，最终状态各重试一次；只产生 500 次安装收费，取消操作无收费且冻结金额全部释放。
- 合计 1,500 个收费事件，费用 $75；先消耗 fixture 的 $5 赠送额度，再扣 $70 现金。重复请求无额外收费。

验证通过：Go 全量回归、并发逻辑 race 检测、PostgreSQL 的分流/斗篷/计费/USDT 回归，以及访问队列故障恢复和保留期测试。保留期测试一次清理 12,001 条过期记录，保留当前记录，验证分钟限流和下一分钟继续清理。测试主动模拟数据库故障时会产生预期错误日志，以测试最终 PASS 状态为准。

原始运行日志位于本地 `artifacts/concurrency-200qps/`（不提交 Git）。正式上线容量还取决于服务器 CPU、磁盘、数据库距离、业务数据规模、日志保留量及真实 APK 流量。上线前应在相同规格的隔离环境重放流量，观察响应延迟、数据库等待、队列积压和网络吞吐；不要直接对客户域名发起压测。

如果全天持续 200 QPS，每日即有 1,728 万次入口请求；斗篷内嵌分流和落地页还会产生多条访问记录。短测不能证明数亿条历史记录下的查询表现。需要根据实际持续流量规划磁盘、定期检查过期积压和 PostgreSQL autovacuum，必要时另行设计分区或历史聚合，不应把开发机的低延迟当作长期存储容量保证。
